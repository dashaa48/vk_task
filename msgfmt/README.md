# msgfmt — разметка сообщений → чистый текст + стилевые диапазоны

C++17, только стандартная библиотека.

## Сборка и тесты

```sh
cmake -S msgfmt -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build --output-on-failure
# с санитайзерами:
cmake -S msgfmt -B build-san -DMSGFMT_SANITIZE=ON && cmake --build build-san && ctest --test-dir build-san
```

Цели: `msgfmt` (CLI), `msgfmt_lib` (библиотека, `include/msgfmt/msgfmt.hpp`), `msgfmt_tests`. В CTest: `msgfmt_unit` (таблица приложения А, UTF-16, валидация UTF-8, экранирование, JSON, свойства на 20 000 случайных входов) и `msgfmt_cli` (`tests/cli_test.sh`). Флаги `-Wall -Wextra` включены; сборка чистая, ASan/UBSan замечаний не дают.

## Использование

```sh
$ printf 'Привет, **мир**!' | msgfmt
{"text": "Привет, мир!", "ranges": [{"style": "bold", "offset": 8, "length": 3, "url": ""}]}
$ printf '2 * 3' | msgfmt escape
2 \* 3
```

Код возврата 0 — успех, 2 — некорректный UTF-8 (`{"error": "invalid_utf8"}` в stdout), 1 — неверные аргументы командной строки (usage в stderr). После JSON разбора выводится перевод строки; `escape` выводит текст без добавления перевода строки.

## Принятые решения

* **Алгоритм.** Рекурсивный разбор слева направо. Открывающий маркер пробует найти «ближайший подходящий» закрывающий; если не нашёл, откат (вывод и диапазоны, созданные попыткой, отбрасываются) и маркер выводится литералом. Неудачные попытки запоминаются по паре (позиция, набор открытых стилей). Закрывает всегда самый внутренний открытый стиль, поэтому частичных пересечений не бывает.
* **Пустое содержимое** (`****`, ` `` `, `[](u)`) стилем не считается: маркеры остаются литералами.
* **code** копирует содержимое как есть; закрывающая обратная кавычка — ближайшая, перед которой стоит непробельный символ.
* **Ссылка.** Текст может содержать вложенные `bold`/`italic`/`code`, но не неэкранированный `]`; URL берётся «как есть» (без обработки `\`), не содержит пробельных символов и `)`. Вложенная ссылка в ссылке не открывается.
* **Буква или цифра** (правило 3) определяется собственной таблицей основных блоков Юникода (латиница, греческий, кириллица, иврит, арабский, деванагари, тайский, CJK, хангыль и др.), без зависимости от локали, чтобы вывод был детерминирован.
* **Пробельные символы:** ASCII, U+0085, U+00A0, U+1680, U+2000–200A, U+2028/2029, U+202F, U+205F, U+3000.
* **UTF-8:** строгая проверка (без overlong, суррогатов, > U+10FFFF, обрывов). Нормализация не выполняется.
* **JSON:** экранируются `"`, `\` и управляющие символы (`\uXXXX`, для `\n \r \t \b \f` — короткие формы); остальной Unicode выводится как есть в UTF-8.

## Замечание о примере 9

В тексте правил пример записан как `**жирный _и курсив_**` с italic «на слове „и“», а в таблице приложения А ожидается `bold(0, 15); italic(7, 1)`. По правилам 3 и 5 вход `**жирный _и курсив_**` даёт `italic(7, 8)` (приоритет у правил), а результат таблицы получается для `**жирный _и_ курсив**`. Оба варианта проверяются тестами.

## Известные ограничения

* В худшем случае (очень много непарных маркеров) разбор квадратичен по длине входа; на практике и в тестах (3000 непарных маркеров, 100 000 обратных кавычек) работает мгновенно.
* Таблица «буква/цифра» приближённая: редкие письменности могут трактоваться как не-буквы.
